# 文章の関係抽出用・合成開発pilot

実在顧客の情報を含まない、日本語の合成入力である。`memo-a.md` と `memo-b.md` の2資料に、手作業で定義した16件の関係・属性の記述を置く。入力はUTF-8のMarkdownで、設定と評価用goldはJSONで保存する。

同じ資料で抽出器・プロンプトを開発するpilotであり、未知資料への汎化性能を測る評価ではない。実行結果や正解率はまだ含まない。繰り返し開発で成功しても、独立したholdoutの成績とは扱わない。

## ファイルの役割

- `memo-a.md`、`memo-b.md`：抽出器に渡す原文。
- `ontology.json`：案件から組織または金額への4種類のpredicate。抽出時に使用してよい。
- `gold.json`：手作業で定義した期待tuple、正確な根拠位置と引用、12問の固定Q&A。評価専用であり、抽出・回答生成のprompt、検索index、Foundry KBに一切渡さない。
- `generate_variants.py`、`variants/`：資料AをCSV・PPTX・PNGへ変換する補助と固定出力。意味を追加せず、goldを読まずに原文から生成する。

取り込み対象は資料ファイルを明示して選ぶ。このディレクトリを再帰的にまとめて取り込むとgoldが混入するため、その方法は使わない。抽出時は資料とontologyだけを渡し、Q&A時は`question`と`scope_document_ids`だけを質問として渡す。`expected_answer`、`answer_kind`、`assertion_ids`、資料別の期待tupleは採点側にのみ置く。

## 固定した区別

16件の内訳は `asserted` 11件、`denied` 3件、`unknown` 1件、`ambiguous` 1件である。`asserted` と `denied` のobjectは原文中の文字列、`unknown` と `ambiguous` のobjectはJSONの`null`とする。候補名から確定した関係を作らない。否定された組織を消して「情報なし」にもしない。

`managedBy`・`supportedBy`・`approvedBy` は常に案件が主語、組織が目的語である。組織側から尋ねる質問でも、保存する関係の向きは逆転させない。`budgetYen` のobjectは、例えば`1200000円`のように単位を含む原文文字列である。

資料間で共通識別子P-101の朝凪とP-102の星凪は同一案件である。一方、灯台は資料Aでは受付支援案件A-201、資料Bでは在庫支援案件B-201であり、同名でも別案件である。goldのentity識別子はこの手作業の照合を表す。資料の記載を無視して名前だけで統合しない。

朝凪の主担当・予算、星凪の支援担当には、資料間で意図的な矛盾がある。両資料は同じ基準日で、優先順位は指定していない。一方を自動的に最新・正しいとして採用せず、原文別の肯定と否定を併記する。

Q&Aの`answer_kind=not_stated`は、指定された資料に対応する記述がないことを表す。抽出行のstatusではない。明示否定の`denied`や明示的な未定の`unknown`とは区別する。

## 根拠と評価の境界

Markdownの根拠位置は1始まりの物理行番号で、引用は行をそのまま連結した連続部分である。各期待tupleの根拠は1行で完結する。本文先頭の適用範囲も入力に残す。JSON内の`sha256`はUTF-8ファイル全体を対象とする。

採点は、主語・predicate・object・statusの一致、根拠引用と位置の一致、資料をまたいだ同一性の扱いを分けて記録する。未記載の関係を作らないこと、未定をゼロにしないこと、候補を確定させないことも別に確認する。構文検証や固定goldとの一致だけで、広い意味理解・本番品質を保証しない。

追加形式は資料Aの情報を再配置した同内容の入力であり、独立したデータ件数には数えない。PNGは文字読取を伴うため、Markdown/CSV/PPTXの文字列読取と成績を分ける。保存済みの固定画像を使えば、評価時に日本語フォントを用意する必要はない。生成環境とフォントの情報は`variants/manifest.json`に記録し、フォント自体は再配布しない。
